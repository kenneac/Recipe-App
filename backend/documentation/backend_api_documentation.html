01

Backend Overview

▾

What it is. The backend is a single-process, single-file Express 5 REST API (src/server.js, 83 lines) deployed on Render. It exposes a small JSON surface under /api whose only job is to persist the mobile app's favorites feature in PostgreSQL. Recipe content is not stored or proxied here — the Expo client queries TheMealDB directly — and identity is managed by Clerk on the client. The most accurate description of this backend is a favorites micro-API with a health probe.

Main purpose

  • Persist favourites — create, list and delete rows in the favorites table, keyed by the Clerk user id and the TheMealDB recipe id.
  • Health probe — GET /api/health returns { success: true } for uptime checks and cold-start warming.
  • Keep-alive (built, disabled) — config/cron.js pings its own URL every 14 minutes so the Render free tier never sleeps; the import is commented out in server.js line 8 to save quota.
  • Stable HTTPS base for the client — the mobile app hard-codes https://recipe-app-lrg5.onrender.com/api in mobile/src/constants/api.js.

Overall architecture

A flat, three-stage pipeline with no abstractions between the HTTP layer and the database driver. Each route handler is the controller, and it calls Drizzle directly:

HTTP
Express 5 + express.json()app setup, body parsing, route table — src/server.js
Handlers
Inline async route handlersvalidation, business logic, try/catch, JSON responses — no controllers/ or services/ folders exist
Data
Drizzle ORM → neon-http → Neon PostgreSQLquery builder & schema in src/db/schema.js, connection in src/config/db.js

ℹ️ Failure handling lives inside each handler

There is no dedicated Express error-handling middleware. Every handler wraps its own body in try / catch, logs the error with console.log and answers 500 { error: "Something went wrong" }. Errors thrown before a handler runs (for example a malformed JSON body rejected by express.json()) fall through to Express's built-in default error handler and produce an HTML error page, not JSON.

DELETE /api/favorites/:userId/:recipeId no auth checkidempotent-looking

Deletes one favourite using the composite key (userId, recipeId) taken from the URL. This is exactly what the app's "unsave" action triggers.

bashcurl

ParsingrecipeId is coerced with parseInt(recipeId) (server.js line 71). A non-numeric segment becomes NaN and the Postgres cast fails → 500.

API conventions observed

JSON in / JSON out errors always { error: string } success shapes vary: object · array · message no versioning (/api, not /api/v1) no pagination / filtering / sorting params no auth headers expected plural resource name: favorites status codes: 200 / 201 / 400 / 500
⚠️ Framework-generated responses break the JSON convention

Requests that fail before reaching a handler — an unknown path, or a malformed JSON body rejected by express.json() — are answered by Express's built-in default handlers with HTML error pages, not the { error } JSON shape used by the handlers themselves.

Authentication Flow

▾
🛑 Headline finding

The backend performs no authentication and no authorization. There is no token check, no session middleware, no API key and no ownership guard anywhere in backend/src. Identity is established by Clerk entirely on the client, and the backend simply trusts the userId string it receives — in a URL parameter for reads/deletes, and in the request body for writes.

🔓 Risk: data isolation relies on the caller's honesty

Because the handlers trust userId:

  • GET /api/favorites/{userId} returns another user's favourites to anyone who knows or guesses their Clerk id.
  • DELETE /api/favorites/{userId}/{recipeId} lets an attacker delete another user's saved recipes.
  • POST /api/favorites lets a caller write rows attributed to any user id.

Mitigation (not yet implemented): verify the Clerk session token server-side — e.g. Clerk's Express middleware or verifyToken — then derive userId from the verified token and ignore any client-supplied id.

⚠️ Schema observations
  • No unique constraint on (user_id, recipe_id) — POSTing the same recipe twice stores two rows.
  • No index on user_id beyond the primary key — listing favourites scans the table as it grows.
  • No foreign keys — impossible for user_id (Clerk lives outside the database) and skipped for recipe_id (TheMealDB is external).
  • No updated_at, no soft-delete flag — deletes are hard deletes.

ℹ️ Practical consequence of the missing CORS layer

Native mobile clients are not subject to browser CORS rules, so the iOS/Android app works fine. A browser-based client (for example the Expo web target, which is configured in mobile/package.json) would be blocked by the browser because the API returns no Access-Control-Allow-Origin header. Registering the already-installed cors package would restore web access.

Architecture Notes & Gaps

▾

Findings gathered while reading the source. Each one references the section where the evidence lives; none of these are speculative features — they are all visible in the current code.

SeverityFindingImpactWhere
HighNo server-side authentication or authorization — userId is trusted from the callerAny caller can read, write or delete favourites for any user id§07
Mediumcors is installed but never registeredBrowser-based clients (Expo web) are blocked; native apps unaffected§09
MediumNo unique constraint on (user_id, recipe_id)Double-saving a recipe stores duplicate rows that the UI must dedupe§08

InfoNo tests, no README, no CI configuration in the backendRegressions rely on manual testingrepository

Suggested next steps (ordered by impact)

  1. Verify Clerk session tokens server-side and derive userId from the verified token — this closes the impersonation hole described in §07.
  2. Register CORS (app.use(cors(...))) so the Expo web target and any future browser tooling can call the API.
  3. Add a unique index on (user_id, recipe_id) and surface duplicates as a 409 or upsert, so the app cannot store the same favourite twice.
  4. Centralise validation and errors — a small zod schema per route plus one JSON error-handling middleware would remove the HTML error pages.
  5. Decide the keep-alive strategy — re-enable the cron ping, use an external uptime monitor against /api/health, or accept cold starts.
  6. Introduce routes/ + services/ structure and tests before the second resource (e.g. meal plans or notes) is added.
